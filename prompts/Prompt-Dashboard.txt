PROMPT DASHBOARD PERSONALIZAVEL

REGRA DE OURO

Este prompt nao cria, altera ou transiciona estado.
Apenas a State Machine pode alterar estado.

Se a execucao alterar schema, migration, backend, frontend, permissoes,
persistencia, testes ou comportamento de produto em STATE-08 PRODUCTION_RELEASE,
registrar como manutencao funcional pos-release.

---

OBJETIVO

Transformar o dashboard do ShiftFlow em uma area operacional personalizavel por
usuario, com KPIs, widgets e layout responsivo persistidos por usuario e empresa.
Perfis podem fornecer layouts padrao, mas nao substituem o escopo persistido por
usuario quando houver personalizacao individual.

---

ESCOPO FUNCIONAL

O dashboard deve permitir:

* Selecionar quais widgets ficam visiveis.
* Reordenar widgets.
* Redimensionar widgets quando o grid permitir.
* Persistir preferencias por usuario.
* Restaurar layout padrao.
* Diferenciar dashboard executivo, operacional e de acompanhamento quando houver contexto.
* Preservar desempenho e legibilidade em mobile, desktop e modo TV.

---

WIDGETS ESPERADOS

O conjunto inicial pode incluir:

* Atividades por status.
* Atividades atrasadas.
* Atividades criticas.
* SLA e tempo medio.
* Ocorrencias recentes.
* Distribuicao por equipe.
* Distribuicao por cliente.
* Pendencias por turno.
* Kanban resumido.
* Alertas operacionais.

Cada widget deve possuir:

* Identificador estavel.
* Titulo curto.
* Estado de carregamento.
* Estado vazio.
* Tratamento de erro.
* Fonte de dados definida.
* Permissao ou regra de visibilidade quando aplicavel.

---

PERSISTENCIA

Persistir configuracao de dashboard sem misturar empresas ou usuarios:

* Escopo minimo: userId e companyId.
* Dados persistidos: widgets visiveis, ordem, tamanho, filtros e versao do layout.
* Layout padrao deve funcionar mesmo sem configuracao salva.
* Layout padrao por perfil ou tipo de dashboard deve ser tratado como template, nao como preferencia individual.
* Configuracao invalida ou antiga deve cair para fallback seguro.

---

BACKEND E API

Quando houver implementacao:

* Criar rotas especificas para buscar, salvar, substituir e restaurar layout.
* Validar ownership por empresa ativa.
* Validar schema do payload.
* Evitar gravar widgets desconhecidos.
* Registrar erros de forma auditavel sem expor dados sensiveis.

---

FRONTEND

O frontend deve:

* Separar modo visualizacao e modo personalizacao.
* Indicar edicao ativa sem poluir o uso normal.
* Usar controles adequados para adicionar, remover, mover e restaurar widgets.
* Evitar mudancas de tamanho inesperadas durante hover, loading ou drag.
* Manter navegacao por teclado quando possivel.
* Garantir que texto e botoes nao se sobreponham em telas pequenas.

---

RESTRICOES

Nao duplicar regras de filtro que ja existam em servicos compartilhados.
Nao criar widget sem fonte de dados definida.
Nao persistir configuracao global quando a necessidade for por usuario.
Nao misturar dashboard personalizavel com modo TV sem regra explicita.
Nao remover dashboard atual sem fallback validado.

---

CRITERIOS DE ACEITE

* Dashboard carrega com layout padrao.
* Usuario consegue personalizar e salvar.
* Layout salvo permanece apos reload.
* Outro usuario ou empresa nao recebe a configuracao indevida.
* Restaurar padrao funciona.
* Widgets tratam loading, vazio e erro.
* Lint, typecheck, testes e build passam quando codigo for alterado.

---

ENTREGAVEIS

Ao executar este prompt, registrar:

* Problemas encontrados.
* Modelo de persistencia adotado.
* APIs e telas alteradas.
* Widgets implementados ou ajustados.
* Evidencias de validacao.
* Pendencias futuras.
