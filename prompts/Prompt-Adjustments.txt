# Solicitação de Melhorias no Sistema

Antes de iniciar qualquer implementação, analise cuidadosamente a arquitetura atual do projeto, identificando padrões de organização, componentes reutilizáveis, estrutura de rotas, modelos de dados e fluxo da aplicação.

As alterações devem preservar o padrão visual existente, manter a arquitetura atual e priorizar a reutilização de componentes, evitando duplicação de código e regressões.

## 1. Kanban interno nas Atividades

Implementar um Kanban próprio dentro de cada atividade, independente do Kanban principal.

Estrutura esperada:

```
Projeto
 └── Atividade
      └── Kanban de tarefas
```

Cada atividade deverá possuir seu próprio conjunto de colunas, por exemplo:

* A Fazer
* Em Andamento
* Revisão
* Concluído

Cada coluna poderá conter diversas tarefas.

### Requisitos

* Criar, editar, excluir e arquivar tarefas.
* Criar, editar, excluir e ordenar colunas.
* Permitir Drag & Drop entre colunas.
* Permitir reordenação de tarefas dentro da mesma coluna.
* Persistir a ordem das colunas.
* Persistir a ordem das tarefas.
* Manter relacionamento entre Projeto → Atividade → Tarefa.
* Registrar histórico das movimentações das tarefas.
* Registrar data de criação, atualização e conclusão.
* Permitir responsáveis, etiquetas, prioridade e anexos utilizando os componentes já existentes, quando aplicável.
* Não alterar o funcionamento do Kanban principal.

## 2. Dashboard Principal

Melhorar a legenda do Dashboard Principal.

### Alterações

* Utilizar exatamente as mesmas cores utilizadas nas colunas do Kanban.
* Exibir um indicador visual colorido para cada status.
* Remover a quantidade de membros exibida ao lado das legendas.
* Garantir consistência visual entre Dashboard e Kanban.

## ## 3. Filtros

Padronizar a utilização de filtros nos módulos do sistema.

### Manter filtros apenas nos seguintes módulos

* Relatórios
* Kanban
* Gestão de Atividades
* Dashboard por Equipe
* Dashboard Principal

### Remover os filtros de todos os demais módulos

Antes da remoção, verificar se existem dependências que utilizem os filtros para:

* Consultas
* Paginação
* Ordenação
* Pesquisas
* Carregamento de dados
* APIs

A remoção dos filtros não deve alterar o funcionamento dos módulos nem causar regressões na interface ou na lógica da aplicação.

Sempre que possível, reutilizar os componentes de filtro já existentes, mantendo o mesmo padrão visual e comportamental nos módulos em que os filtros permanecerem.

## ## 4. Gestão de Perfis

Reestruturar completamente o layout do módulo Gestão de Perfis.

### Objetivos

* Interface mais moderna.
* Melhor organização visual.
* Melhor aproveitamento do espaço.
* Melhor experiência de uso.
* Padronização com o restante do sistema.

Sempre que possível utilizar:

* Cards
* Grids responsivos
* Agrupamento lógico das informações
* Componentes reutilizáveis
* Melhor hierarquia visual

### Funcionalidades

Implementar gerenciamento completo dos perfis, permitindo:

* Criar perfis.
* Editar perfis existentes.
* Excluir perfis (quando permitido).
* Ativar ou desativar perfis.
* Duplicar perfis para facilitar a criação de novos.
* Definir nome, descrição e cor de identificação do perfil.
* Configurar permissões associadas ao perfil.
* Visualizar a quantidade de usuários vinculados a cada perfil.
* Impedir a exclusão de perfis que estejam em uso, exibindo uma mensagem informativa.
* Registrar histórico das alterações realizadas nos perfis, quando aplicável.

A tela de edição deve ser intuitiva, organizada por seções e permitir alterar todas as propriedades do perfil sem necessidade de criar um novo.

Garantir que todas as alterações sejam refletidas imediatamente nas permissões e funcionalidades do sistema, respeitando as regras de acesso já existentes.

## 5. Kanban Principal

Melhorar a identificação visual das atividades.

### Requisitos

Cada equipe deverá possuir uma cor própria.

Essa cor deverá aparecer de forma evidente nos cartões das atividades, por exemplo através de:

* barra lateral
* faixa superior
* borda
* indicador colorido

O usuário deve identificar imediatamente qual equipe é responsável pela atividade sem precisar abrir o cartão.

As cores devem ser centralizadas em um único local da aplicação para facilitar futuras alterações.

## 6. Configurações

Expandir significativamente o módulo Configurações, transformando-o em um painel administrativo preparado para crescimento futuro.

Criar uma estrutura modular contendo, no mínimo:

### Administração

* Configurações Gerais
* Usuários
* Equipes
* Perfis
* Permissões

### Gestão

* Status
* Prioridades
* Etiquetas
* Tipos de Atividade
* Cores

### Sistema

* Notificações
* Integrações
* Personalização
* Preferências do Usuário
* Logs (quando aplicável)
* Auditoria (quando aplicável)

A estrutura deve facilitar futuras expansões sem necessidade de grandes refatorações.

## Requisitos Técnicos

Durante toda a implementação:

* Manter a arquitetura atual.
* Seguir os padrões existentes do projeto.
* Reutilizar componentes sempre que possível.
* Evitar código duplicado.
* Garantir tipagem consistente.
* Manter compatibilidade com dispositivos móveis.
* Garantir responsividade.
* Não introduzir regressões.
* Atualizar rotas apenas quando necessário.
* Atualizar APIs apenas quando necessário.
* Atualizar modelos e tipos afetados.
* Atualizar documentação técnica quando houver alterações relevantes.

Caso sejam necessárias alterações no banco de dados:

* Criar as migrations correspondentes.
* Atualizar os modelos.
* Atualizar os relacionamentos.
* Garantir compatibilidade com os dados existentes.
* Evitar perda de informações.

## Critérios de Aceitação

Antes de concluir a implementação, validar que:

* Todas as funcionalidades existentes continuam operando normalmente.
* Não existam erros de compilação.
* Não existam erros de lint.
* Não existam erros de tipagem.
* Não existam regressões visuais.
* Todas as telas permaneçam responsivas.
* O Drag & Drop funcione corretamente.
* A persistência das alterações esteja funcionando.
* As permissões continuem sendo respeitadas.
* As APIs permaneçam compatíveis.
