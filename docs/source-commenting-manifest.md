# Source Commenting Manifest

## Policy

The canonical [language policy](../prompts/core/Governance.md#language-policy) selects the language for project-owned comments. This manifest owns only comment coverage, placement, syntax and immutability exceptions, and automated enforcement; it is not a competing language authority.

Every editable source and configuration file that supports comments must open with a concise `en-GB:` comment explaining its responsibility and why it exists. Non-obvious algorithms, security boundaries, business invariants, compatibility decisions, and operational side effects require local en-GB comments near the relevant code.

CSS keeps the stricter rule: every declaration must have an adjacent en-GB comment explaining what the property controls and why it is required.

Comments must explain intent rather than restating syntax. Redundant line-by-line narration is prohibited because it obscures behaviour and makes reviews less reliable.

## Syntax and Immutability Exceptions

The following files are covered by this manifest instead of inline comments:

- `package.json`: strict JSON consumed by npm; comments are invalid.
- `package-lock.json`: generated strict JSON; manual comments would be invalid and non-durable.
- `global.json`: strict JSON consumed by the .NET SDK; comments are invalid.
- `apps/api-dotnet/src/ShiftFlow.Api/packages.lock.json`: generated strict JSON; manual comments would be invalid and non-durable.
- `apps/api-dotnet/src/ShiftFlow.Application/packages.lock.json`: generated strict JSON; manual comments would be invalid and non-durable.
- `apps/api-dotnet/src/ShiftFlow.Domain/packages.lock.json`: generated strict JSON; manual comments would be invalid and non-durable.
- `apps/api-dotnet/src/ShiftFlow.Infrastructure/packages.lock.json`: generated strict JSON; manual comments would be invalid and non-durable.
- `apps/api-dotnet/tests/ShiftFlow.Api.Tests/packages.lock.json`: generated strict JSON; manual comments would be invalid and non-durable.
- `.prettierrc`: strict JSON configuration; comments are not portable across parsers.
- `apps/web/next-env.d.ts`: generated by Next.js and must not be edited manually.
- `prisma/migrations/migration_lock.toml`: generated by Prisma and must not be edited manually.
- The following applied migrations are immutable history; changing them to add comments would alter their checksums and create schema drift:
  - `prisma/migrations/20260621120000_state_03_database_modeling/migration.sql`
  - `prisma/migrations/20260622010000_prompt_revision_activity_fields/migration.sql`
  - `prisma/migrations/20260622090000_remove_team_from_shifts/migration.sql`
  - `prisma/migrations/20260622093000_allow_reuse_deleted_team_names/migration.sql`
  - `prisma/migrations/20260622094000_allow_reuse_deleted_client_names_codes/migration.sql`
  - `prisma/migrations/20260622103000_operational_dossier_status_service/migration.sql`
  - `prisma/migrations/20260623010000_refresh_tokens_company_scope/migration.sql`
  - `prisma/migrations/20260701120000_auth_session_hardening/migration.sql`
  - `prisma/migrations/20260701182603_add_dashboard_personalization/migration.sql`
  - `prisma/migrations/20260701193000_activity_internal_kanban_and_role_management/migration.sql`
  - `prisma/migrations/20260701203000_dashboard_widget_layout_flexibility/migration.sql`
  - `prisma/migrations/20260702193000_audit_full_residual_fixes/migration.sql`

New migration SQL files are not automatically exempt and must include their en-GB responsibility comment when created.

TypeScript configuration files use JSONC through the TypeScript toolchain and therefore carry inline en-GB comments.

## Enforcement

Run `npm run comments:verify`. The gate checks every present tracked or untracked Git-candidate that supports comments, skips deleted paths, validates the documented exceptions, and confirms declaration-level coverage in `apps/web/app/globals.css`.
